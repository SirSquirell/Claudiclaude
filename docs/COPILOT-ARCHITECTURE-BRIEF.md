Hand this to Copilot together with the repository. It asks for the report described below, and it
front-loads the things Copilot cannot know from the code alone and would otherwise get wrong.

## Read these first — most of the proposal already exists

**Do not propose a multi-broker architecture from scratch.** A large part of it landed in 0.30.0 and
the design is written down. Proposing a rebuild of it would be the single least useful outcome of
this exercise.

| Read | Why |
|---|---|
| `CLAUDE.md` | Nine rules that are not up for renegotiation. Rules 1, 5, 7, 8 and 9 each constrain the architecture, and rule 9 **decides which brokers are possible at all** |
| `docs/MULTI-BROKER.md` | ~570 lines. §1 the five requirements a broker must meet, §4 acceptance criteria, §5 test cases, §6 stop conditions, §7 two accounts at one broker, **§8 Trading 212, measured** |
| `src/lib/brokers/index.js` | The adapter boundary as it exists, including `REQUIRED` and `missingMembers()` |
| `src/lib/combine.js` | The combining arithmetic, already live |
| `docs/STATUS.md` | What is built, what is refined, what is parked |
| `docs/IBKR-SPIKE-BRIEF.md` | IBKR has **not** been investigated yet |

### What exists today, concretely

Counted on 2026-08-11 so the report starts from facts rather than an impression:

| | |
|---|---|
| Version | 0.42.0, ~43 releases |
| Tests | **350**, `node --test`, no install needed. Plus a leak guard and a palette check in the same `npm test` |
| Engine | `engine.js`, ~2 700 lines. Pure: no `fetch`, no `chrome.*`, no `indexedDB`, no `Date.now()` |
| Adapter boundary | `brokers/index.js` with **15 `REQUIRED` members** and `missingMembers()` |
| Combining | `combine.js`, live on every page load, **22 tests** |
| Brokers implemented | **one** — DEGIRO |
| Brokers investigated | Trade Republic (parked, three claims retracted), Trading 212 (**measured**, one question left), IBKR (**not started**) |
| Egress control | `EXPORTABLE_META` allowlist in `store.js`, a second allowlist in `report.js`, a leak guard in `tools/check-leaks.mjs` |
| UI | 7 sections, EN/NL, light/dark/auto, ~350 dictionary entries |
| Dependencies | **none.** Chart.js is vendored |

Facts worth stating up front, because they change the shape of any proposal:

- **The multi-broker path is already the only path.** Every page load runs the single DEGIRO result
  through `combineResults`, which returns one part untouched. It is not dormant scaffolding.
- **Trade Republic is parked** at the user's instruction, and three earlier claims about it were
  retracted as drawn from samples too small to carry them.
- **Trading 212 has been measured** (2026-08-11). Prices are public and need no credential; account
  data is documented only behind an API key, which rule 9 forbids. One question remains.
- **IBKR is unexamined.** Do not assume it resembles the other two.

## The report to produce

Markdown. Every claim marked **verified in code** (with the file and roughly where), **inferred**,
or **unknown**. Where a doc and the code disagree, say so — that is a finding, not a nuisance.

### 1. Folder structure
What each directory is for and what may not go in it. Note explicitly that `engine.js` is pure and
that `sync.js` is the only module touching both network and disk.

### 2. Principal modules
Per module: its one responsibility, its public surface, and — the useful part — **what it is
forbidden to do**. Several have hard constraints in comments; quote them.

### 3. Authentication flow
Trace it end to end from cookie to a request carrying a session. State where the credential lives at
each hop and **what is never written down**. Rule 9 is the constraint; say how the code enforces it
rather than merely promises it.

### 4. Sync flow
`sw.js` → `sync.js` → adapter → `parse` → `store` → `engine` → `derived`. Include: the windowing and
what happens to a window the server refuses, the single throttled queue and why there must be
exactly one, the checkpoint the UI reads instead of the message reply, and where the reconciliation
happens.

### 5. Data model
The IndexedDB stores and what is *truth* versus *cache* (rule 2). The normalised transaction, cash
row, product and price-series shapes. The meta store and its **export allowlist** — note that this
is default-deny and why.

### 6. Broker-specific parts
Everything that would have to be written again for a second broker. Be precise: is it in
`brokers/degiro.js`, or has it leaked into `degiro.js`, `session.js`, `parse.js`, `classify.js`,
`config.js` or the UI? **Leaks are the most valuable thing this report can find.**

A starting point, counted on 2026-08-11 — occurrences of the string `degiro`/`DEGIRO`:

| File | Hits | Above the adapter boundary? |
|---|---|---|
| `src/ui/app.js` | 24 | **Yes.** The UI should not know which broker it is showing |
| `src/lib/config.js` | 12 | Arguably fine — it is declared pure data — but it is one file per broker or a nested shape, and that is a decision |
| `src/lib/session.js` | 9 | **Yes.** Session resolution is adapter work |
| `src/lib/classify.js` | — | DEGIRO's vocabulary by definition; the question is whether it is *reachable* per broker |

Those counts are the symptom, not the finding. For each one say **whether it is a genuine coupling
or only a name in a string**, because a label in a message is not the same defect as a code path.

### 7. Generic parts
What a second broker gets for free. Say for each whether it is genuinely broker-agnostic today or
merely *looks* it.

### 8. Dependencies between modules
A dependency graph. Flag any edge that violates the layering — in particular anything above the
adapter boundary that names a broker, and anything importing `engine.js` that would give it I/O.

## Then: the multi-broker proposal

Structured as **what exists / what is missing / what it costs**, with a percentage per area and a
one-line justification for each figure. A percentage without a reason is noise.

Cover at least:

1. **The adapter boundary.** Does `REQUIRED` cover what a second broker needs? What is missing, and
   what should *not* be added (rule 8: no capability flags or plugin loader nobody has a use for).
2. **Storage per broker.** Keys are currently unprefixed. What has to change, and what happens to
   data already stored under the old scheme.
3. **Combining.** Already built and tested. Check the arithmetic claim in `combine.js` — that
   `pnl_combined = Σ pnl_broker` holds identically because SPEC §1.4 is linear.
4. **Reconciliation per broker.** Rule 6 must not be softened by combining: a cent out at one broker
   cannot be hidden by another.
5. **Sync orchestration.** One queue per broker or one global queue? Rule 5 says rate limiting is an
   account-safety issue, and the current queue is a single module-global. State the consequence
   either way.
6. **Classification.** `classify.js` is DEGIRO's vocabulary. Adapters return rows already carrying a
   category — verify that in code and say whether the engine ever classifies anything itself.
7. **The UI.** Per-broker filtering, per-broker sync and wipe. US-23 and US-24 are refined and
   **deliberately deferred**; say what they cost, not whether to do them.
8. **Egress.** A second broker's fields must be added to the allowlists by name. Point at every
   place that has to be edited.

### Per broker

For Trading 212, IBKR and Trade Republic, answer against the five requirements in
`MULTI-BROKER.md` §1 (R1 session, R2 trades with the settled base amount, R3 categorised cash, R4
daily prices backwards, R5 the broker's own total) — and mark each **documented / measured /
unknown**. §8 has Trading 212 already; do not restate it, extend it.

**R1 is a gate, not a difficulty.** Rule 9 puts a broker whose data cannot be reached from an
already-logged-in tab out of scope however valuable it is, and the correct outcome there is closing
the story rather than proposing a login form.

## What would make this report bad

- Proposing what already exists. `combine.js` and `brokers/index.js` are on `main` and live.
- Percentages with no reasoning.
- Treating rule 9 as a preference to be traded off.
- Recommending an abstraction with one implementation and no story behind it — rule 8, and
  `brokers/index.js` documents the one exception and why it earned it.
- Silence about leaks. A report that says the boundary is clean without having checked
  `session.js`, `config.js` and the UI for broker names has not done the job.

## The output has to be executable by another agent

This report does not end in a slide. It ends in **instructions handed to the Claude Code session
that maintains this repository**, so write it to be acted on rather than admired.

That means:

- **Anchor every recommendation.** File path, and the function or section within it. "The adapter
  boundary needs work" is not actionable; "`brokers/index.js:REQUIRED` has no member for X, and
  `sync.js` calls it at the windowing step" is.
- **Cite the rules by number.** `CLAUDE.md` rules 1, 2, 4, 5, 6, 7, 8 and 9 each rule some options
  out. A recommendation that collides with one is fine *if it says so and argues it*; one that
  collides silently gets rejected on sight and wastes the round trip.
- **Say what to change, not what to build.** Most of this exists. The useful unit is a diff-shaped
  instruction against a named file.
- **Use the backlog's shape for anything that is not a one-liner**: a story, acceptance criteria,
  and — this one matters most — **stop conditions agreed in advance.** `MULTI-BROKER.md` §6 is the
  model. Every spike in this project that went well had its "what would make us stop" written down
  while it was still cheap to agree to.
- **Order the work by what unblocks what**, and say which items are wasted effort if an earlier one
  fails. R1 is the standing example: no adapter work for a broker survives R1 coming back "no".
- **Separate findings from proposals.** A leak found in `app.js` is a fact. What to do about it is
  an opinion. Mixing them makes both harder to check.
- **Flag anything you could not verify.** "Unknown" is a usable answer and a wrong confident one
  costs a release. This project has shipped four defects this month that came from exactly that,
  and they are written up in `docs/FINDINGS-TESTERS.md`.

If a recommendation would change a number on somebody's screen, say so explicitly. Those are not
refactors and they do not ship as one.
